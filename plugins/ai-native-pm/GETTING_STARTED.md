# 从一个需求开始

这份指南帮助产品经理把 AI-native PM 用到自己的项目。最小起点是**一个项目、一个需求、一个 chat**；不必先搭齐团队或创建多个会话。安装与版本核对见 [README](README.md)，共创方法导航见 [WORKFLOW](WORKFLOW.md)。本指南只说明如何接入和组织工作，不另写一套共创流程，也不启动常驻 agent 或自动化。

## 1. 先找到项目，再开始对话

已有项目优先复用。在 Codex 中选择已有项目；确实没有合适项目时，再建立项目并关联准备使用的文件目录。界面操作以当前宿主实际能力为准，不以项目显示名称代替文件位置核验。

开始前，让 AI 根据实际可读内容确认：

- 当前使用的实际文件根、项目入口及已有需求、任务和状态记录分别在哪里。
- 本次允许读取和写入的范围，以及需要另行授权的外部访问或发布动作。
- 使用的方法包来源与版本，所需 skill 及其参考文件是否可读。

若目录或权限不明，先说明缺口，不向猜测的位置写文件。项目尚无入口时，可在获准的写区建立最小入口，记录上述位置和当前任务；已有入口则沿用。业务事实、任务书、当前状态和经验都保存在本项目中，方法包作为只读参考。

**宿主事实。** 官方环境说明区分：Local 直接使用本地项目目录；Worktree 在 Git 工作树中隔离改动；Cloud 为每个任务提供独立工作区，本地文件、登录态和 VPN 不自动传入。Cloud 不意味着所有云端项目共用一个目录。参见 [Codex 环境模式](https://learn.chatgpt.com/docs/environments/modes)。

**本方法建议。** 按任务选择环境，并在选定环境重新确认实际文件根与权限。多个 chat 即使属于同一项目，也不能据此推定使用同一个工作副本；涉及隔离副本时，须说明基线、产物位置和交付方式。

## 2. 一句话接入，按当前阶段推进

在选定项目的 chat 中粘贴下面这段，并把方括号替换成你的需求：

```text
请帮我推进［需求］。先读项目入口，确认实际文件根、可写范围和已有相关事项，再选适用的 AI-native PM 技能；沿用已确认内容，从当前阶段开始，缺口只问最关键的一项。
```

AI 先核项目上下文，再读适用的 skill。需求共写进入 [prd-cowrite](skills/prd-cowrite/SKILL.md)，可交互原型共创进入 [prototype-codesign](skills/prototype-codesign/SKILL.md)；材料按需加载，既有草稿与批准决定继续有效。安装插件不等于已建立项目、接通业务系统，或让所有已打开的 chat 自动加载新版本；以当前会话实际能读到的来源为准。

需要逐题挑战关键选择时，可以明确说“用[sz-grilling](skills/sz-grilling/SKILL.md)压力测试这个方案”；需要独立报告时，可以说“用[editorial-report-html](skills/editorial-report-html/SKILL.md)把这些材料做成HTML汇报”。二者都可按需进入，普通澄清不自动变访谈，PRD生成HTML不自动转报告流程。

## 3. 后续需求先匹配已有事项

新需求到来时，先查项目入口和现有任务，判断它是否属于某个已有目标。目标相同、写区相容且上下文可继续使用时，优先复用原事项与 chat；目标独立、写区需要隔离或责任不同，才考虑新建。不能只因名称不同就新开，也不能因文件在同一目录就合并。

```text
我有新需求：［需求］。先找项目中匹配的现有事项，按目标和写区判断复用还是新建；给我最小安排，新建 chat 须经我明确同意。
```

一个 chat 足以完成的工作继续在其中推进。需要分给新会话时，主控先准备自足任务书，写清**目标、范围、基线、写区、产物、验收和授权**。写区明确到目录或文件，并说明不可改范围；基线指向当前有效材料，授权说明本次可做与仍待确认的动作。任务书不依赖旧聊天中的“如上所述”。

新会话先读项目入口和任务书，再加载适用 skill。跨会话共享依据是可访问的文件和已确认决定，不是假定互通的记忆；发消息、创建会话等动作仍须有对应授权。

## 4. 多需求时，再选择是否分工

下表是可选组织方式，不是必须创建的角色清单。

| 可选 chat | 适合承担的工作 | 何时考虑使用 |
|---|---|---|
| 常驻协调 chat | 维护共同基线、任务分配和跨需求冲突，先写任务书 | 多个需求需要持续协调时 |
| 需求 chat | 推进一个明确目标，维护该需求的产物与状态 | 独立目标或写区需要分开时 |
| DS 维护 chat | 维护设计系统的权威来源、版本与消费约定 | 多需求共用 DS，且确有持续维护工作时 |

常驻只表示可持续回到该 chat 继续协调，不表示后台运行、自动监听或共享记忆。DS 维护也不意味着插件自带公司组件库或获得修改、发布设计系统的权限。

需要协调者时，可在准备承担该角色的 chat 中粘贴：

```text
请担任本项目的协调者。先读项目入口，梳理现有事项与写区；需要分工时先写清任务书，再提议复用或创建 chat，创建须经我明确同意。
```

创建前由人明确同意接收角色、任务与范围；用户已经明确要求创建时直接沿用该授权，不再重复请批。工具支持时，实际创建成功并返回可核验入口后才报告“已创建”；工具不支持时，提供包含完整任务书与读取入口的自足提示词，由人手动新建并粘贴，不把提示词交付说成会话创建完成。

## 5. 方法统一维护，项目自行采用

通用方法在统一维护源修改，再生成 plugin；项目保存自己的业务事实、任务、状态和经验。项目经验如何成为方法候选，见 [经验回流指南](references/learning-loop.md)。这些元方法先按需参考，不要求新增 skill，也不要求每轮填写记录。

项目明确采用某个版本后，再按实际环境核验可用性；不手改安装副本，不自动升级或上传项目材料。首次接入以 README 的显式指南链接为入口。未来若适配宿主的安装引导能力，应另做安装后验证，不能据此承诺安装即完成项目接入。
