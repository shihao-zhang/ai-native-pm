# PRD 分阶段共写

本件说明如何从骨架推进到可评审、可定稿的 PRD。入口见 [SKILL.md](../SKILL.md)。只有阶段或授权不清、出现结构问题、发生改判或进入定稿时，才读相关段；普通局部续改不重读整套，也不重跑全流程。

## 1. 先辨认当前任务

- **从空白起草**：先明确读者要判断什么、采用什么载体，再给骨架、必要的图与结论句，按已有或新增授权分批写正文。
- **局部续改**：沿用已确认结构、口径与具体授权，修改受影响内容及其派生面。不能因为改过多轮，就自动整篇重写。
- **结构可能失效**：先诊断，再提出最小有效调整。整篇重写或改变已拍板结构，先核对 PM 是否已明确授权；已有授权覆盖本次动作时直接执行。

需要诊断时，只判断三件事：

1. **缺事实还是重复维护？** 缺必要事实就补；同一事实在多处独立维护，先定权威源与派生关系。源不可访问时，补足当前判断需要的上下文、来源及其时点，并标出未核部分，不复制整份基线。
2. **单处错位还是结构失效？** 单处错位可局部归位；多个读者问题持续混在一起，才考虑重组。例如同图混入对象关系、页面操作、版本变化时，先区分问题和箭头含义，不预设拆成几图。
3. **读者是否更容易判断？** 看能否找到依据、辨认变化、作出下一步决定，且必要约束仍在。字数减少、文件减少或结构检查通过，都不单独证明更易用。

## 2. 按当前阶段交付

下面是推进顺序，不是每次续聊都要重新申请的审批清单。一次授权可覆盖多节或后续批次；授权记录可以是 PM 原话、评审评论或明确的工作指令，不强制另建流程账。

| 阶段 | 本轮交付 | 何时继续 |
|---|---|---|
| 骨架 | 读者地图、推荐章节、关键取舍及推荐、载体形态、需要核对的权威基线；先不给成篇正文 | 骨架与载体已有 PM 认可；新起草才补这一步 |
| 图与最小文字 | 按问题给必要关系图、动线或状态图，每图注明归属章节；配结论句，简单事实用文字 | 所用图经过检查，正文首批范围有授权 |
| 分批正文 | 按被授权章节填定义、操作、边界与需求判据；直接层给结论，细节按需展开 | 本批口径可审，再继续已获授权的下一批；需要新增授权时合并相关问题呈请 |
| 评审准备 | 检查本次评审范围的内容是否齐备，未决项集中可见，说明读什么、原型怎么看、哪些是真实能力或示意 | PM 已同意该范围进入评审；发送或外部写入另按具体授权执行 |
| 评审期增量 | 每轮把关联待定问题与推荐集中呈现；每次拍板按下节同步源与受影响产物 | 沿用已拍口径继续修订，直到 PM 明确本轮定稿 |
| 定稿 | 按第 5 节收口，交付实际完成项、有效证据及剩余开放项 | 完成授权内动作；未获授权的发布等动作明确留待执行 |

四章可作为推荐骨架，按产品与读者裁剪，见 [内容模板](../assets/prd-template.md)；需要 HTML 才读 [HTML 呈现](html-format.md)，新画或重组图才读 [图示指南](diagrams.md)。不要为凑齐章节配图，也不要为了套模板重排已获认可的结构。

分派正文或图示时，工作指令自足写清：目标章节、此次读者问题、已定口径和授权范围、输入证据、允许修改的部分、交付物与验收方式。发单前比较现行定义与上次交付，写出新增、变化、失效项；不能只把旧工单重新发送，也不能让执行方自行补造缺失事实。

## 3. 拍板后的最小落地链

**核准新口径 → 改 Markdown 源 → 重生成派生 HTML → 对齐受影响的图、需求和下游依据 → 执行已获授权的发布或同步 → 回读核验并记录结果。** 不存在的发布面或下游件不额外创建。

- **改源先核锚点**：局部替换前确认目标唯一；未命中或多处命中先核上下文，不硬改。改完检查旧口径残留。小改可直接编辑，不强制每轮另写替换脚本。
- **改判检查相关面**：同次修改里核相关定义、图、下游指令与验收依据；旧结果只证明其当时版本。影响范围复杂时读[变更影响检查](change-impact.md)，普通局部调整无需展开全清单。
- **保持历史性质**：当前正文呈现现在的规则，过程只保留必要变更记录。追加日志和不可变归档不就地重组；旧结果保留时点。改为“本期不做”的事项保留状态、理由与再看条件，不能删得像问题从未存在。
- **内容决定不扩张授权**：PM 拍板内容或说“定稿”，不自动授权发布、覆盖外部内容、跨会话发送。已有具体授权直接沿用；未授权环节先完成本地可审产物，说明尚待执行的动作。
- **对外修改后回读**：核目标版本、修改内容及必要的文件大小等信息，不能只把调用成功当成内容一致。覆盖有评论的评审面前，检查评论是否需要保留。

工程已经开工时，功能或接口变化先列“上次同步以后、尚未对齐”的增量，写清改成什么、对接口与数据有什么影响、需要对方确认什么；由 PM 对齐工程后再推相应原型。纯视觉调整按已有授权推进，不扩大为功能改动。

## 4. 事实、证据与建议的分界

- 写“现有平台能做什么”前先看可获得的实物或一手证据；不可核时写清未知。借来的概念图、原型占位和演示行为不能直接成为已实现能力。
- 接入既有能力时先核其真实兜底与用户可见差异；字段映射不自动成为新增交互。只有已证冲突或逻辑缺口才提出新门槛；已拍新目标不受旧实现能力上限约束，未完成部分写工程依赖。动作与状态名说清对象，例如暂停收音不自动意味着播放、会话和后台执行都停止。
- 区分已证实事实、PM 已定要求、起草建议、待核事实及示意。标注双向符实：实跑数据不降成示意，局部跑通不升成整条能力通过；说明真实的是哪部分、示意的是哪部分。
- 接口、状态、错误态、枚举等会被 agent 据以生成的内容，给准确值及来源，或明确标“未定·不得生成”；不能只留普通 TBD 让执行方补猜。
- 给“是否增加硬前置”一类建议时，在可用且已授权的现行流程中用代表性输入验证。不能实测就标待验证，不把推测写成已有事实。
- 根据会议材料改需求时，核对可获得的逐字稿或原始记录。示例、建议和正式决定分开；只有 AI 纪要且无法核准的内容标待确认。

## 5. 定稿按增量与风险收口

1. **选本轮核验范围**：核正文与原型当前版本是否一致、关键定义是否重复维护、相关外部指针是否仍指旧版，并对未审过的实质增量做对抗审。可由独立读者或代理只读取证，给位置与依据，允许零发现；不固定并行路数或问题数量。已审且未受影响、证据仍有效的部分不重复开放式审查。
2. **主控回源判断**：逐条核原文再采纳。结论句与展开细节不等于重复定义；验收看依据能否找到、变化能否辨认、下一步是否明确，而不是删字多少。结构检查与真实可读性分别报告。
3. **验证读者能用**：发布前安排无项目背景的读者或代理按实际受众试读，应能复述相关章节要点并说出下一步动作。HTML 要真实渲染；有相关交互就实际操作。未做的验证如实标出，不能用静态检查代替。
4. **仅在替换旧入口时迁移**：旧版按已有约束保留；如需归档并改入口，原位置留可追溯指向，必要时附旧节号映射。历史修订行不回改，可加说明帮助读者理解。
5. **更新交付状态**：经 PM 明确定稿后更新状态、版本与变更记录，开放项不能因状态改成“定稿”而消失。导读说明读什么、原型怎么看、真实与示意边界、需要读者反馈什么。
6. **执行授权内交付并回读**：发布或通知按已有具体授权；未获授权则交本地成品和待执行项，不把它报告为已经发布。最终回执区分已核验、仍未知和等待外部动作。

生成命令、构建语法与检查参数仅在实际构建时查 [构建说明](build.md)。本流程不要求额外的会议材料、经验登记、台账制度或固定归档层级。

需要独立核回执时按[证据与复验](evidence-review.md)检查对应对象，不把普通内容整理升级成全业务测试。连续增量收口先分清复用基线、本次变化、过程痕迹和必要保护；减法要保全行为，不能用字数下降代替使用效果。
