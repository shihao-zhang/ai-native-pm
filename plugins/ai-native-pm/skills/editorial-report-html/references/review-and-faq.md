# 初稿审校与 FAQ 梗阻诊断

初版 HTML 完成并通过第一次确定性结构审计后使用。目标不是让 subagent 重写页面，而是暴露主 session 的同源盲区，再由主 session 完成最终修订。

## 1. Subagent 只读审校

当前环境有 subagent 且报告非平凡时，先告诉用户将启动一次只读审校。非平凡包括：超过 5 个章节、正文约 1500 个汉字以上、多来源或多对象对比、包含会影响资源投入的决策建议。向 reviewer 提供：

- 完整用户请求，尤其是题目、任务 framing、受众、时间和决策对象；
- 原始输入材料或其准确路径；
- 适用时提供来源清单、`image_inventory`、图片目录和无法访问项；
- 初版 HTML 路径；
- 本 skill 路径；
- 以下中性任务，不附带主 session 的自评、预期答案或已知缺陷。

```text
请只读审查这份初版 HTML、完整用户请求及原始材料，不要修改任何文件。用户请求中的题目和任务 framing 也是已提供上下文，不得因它没有重复出现在“材料”段而判为模型杜撰。

首次阅读三问（纳入本轮审校，不另起一轮）：先只看交付稿及目标读者/用途，按目标受众的已有知识回答，再对照原始材料完成下列核验。
- 这份稿子的核心结论或核心认识是什么，关键成立条件是什么？请实际复述，不只回答“能看懂”。
- 哪里读不下去或需要反复回读？指出具体位置与原因；没有则写“无”。
- 哪些内容可删、合并或下沉而不损失核心理解、证据与必要条件？说明理由，允许回答“无”，不为凑意见删内容。

检查：
1. 主要阅读目标是否清晰，结构是否服务该目标；自定义契约是否已与人类对齐，不因其不属于三种常用配方就判错；
2. `source-closed` 是否越过材料边界；`source-expanded` 是否覆盖关键来源、披露无法访问项并形成跨来源综合；
3. 核心结论是否可回溯，来源类型与“确认/推断/类比/待验证”是否混淆；
4. 内容关系是否被正确转成段落、表格、流程、时间线或卡片，视觉几何是否忠实表达闭环、阶段、比例与权衡，是否仍像 Markdown 换皮；图表是否各有理解或查阅作用，压缩是否丢失核心洞察、关系或条件，折叠是否藏起决定性判断；正文要求打分、勾选、标记或选择时是否提供真实入口；
5. 如有批量源图，逐张检查其独有信息是否覆盖；相邻图片与 HTML 表格是否重复，删除源图前数字、层级、合并关系、颜色语义和注释是否已保留；
6. 首屏标题是否有孤词或异常断行，长手册是否显示当前章、宽表是否提示横向滚动、长表打印是否错误阻止跨页、打印后关键来源是否仍可追溯，以及无障碍和自包含性有哪些实际风险；仅在用户明确要求或项目已有移动端要求时检查移动端目录与布局，不把未做手机适配或验收作为默认缺陷；
7. 若有速览：是否将分散在全文的精华重组为紧凑的整篇视图，而非仅留下概览第一章与原长文布局；图示是否解释关系，压缩是否保留关键条件，深读入口与全文是否一致？不能因开关代码通过就判阅读体验通过；短文或零脚本场景是否增加了无用/无效模式？
8. 执行 FAQ 梗阻诊断：读者卡在理解、行动、两者还是都不卡？正文应先回填什么？剩余哪些问题值得放 FAQ？

输出：
- 首次阅读：回答上述三问；相关问题在 Findings 中引用即可，不重复展开。
- Findings：按严重程度排序，给出文件位置与影响；
- Coverage Gaps：只列关键来源遗漏、无法追溯主张和源图信息缺口；不适用则写“无”；
- Editorial Deltas：按需列出补充、合并、删减或下沉及其理解收益；正文缺口不能留给 FAQ，删减不能仅以篇幅或字段重合为由，不凑齐各类；
- FAQ Decision：不加 / 机理 / 决策 / 两者，并说明理由；
- FAQ Candidates：只列非显而易见且可回溯的候选；
- Recommended Deltas：最小必要修改。
```

subagent 禁止编辑文件、联网补充新事实或代替主 session 做最终取舍。主 session 必须对照完整用户请求复核 findings，拒绝 reviewer 的上下文误报；吸收高价值 delta 后做一次仅针对改动的忠实性复核，再重新审计。不要把候选问题原样批量粘贴，也不要启动第二轮开放式 review。若 spawn 超时、路径不可读或结果没有文件证据，立即降级为主 session 按同一清单自审。

语义重复不适合交给确定性审计脚本。主 session 必须逐张裁决图片的 `transcribe / preserve / exclude / dual` 状态；`source-expanded` 还要回读来源清单，确认关键来源覆盖数、无法访问项和决定性主张的追溯入口。

对实质性意见，在审校记录或交付说明中简记“采纳 / 部分采纳 / 拒绝 + 理由”，采纳项注明修改位置；同因意见可合并，纯措辞微调不逐条记账，不为回执新增审查轮次。由作者按同一清单自审时，明确标为“作者自审”，不得称为独立读者审查。

## 2. 先判梗阻，再决定 FAQ

判断读者最可能卡在哪里：

| 梗阻 | 处理 |
| --- | --- |
| 理解不了反直觉机理 | 增加机理 FAQ，放在相关机理之后或决策之前 |
| 理解内容但不知道是否行动 | 增加决策 FAQ，放在报告收尾 |
| 决策依赖机理 | 两者都加，机理在前、决策在尾，共用总预算 |
| 正文已足够清楚 | 不加 FAQ |

错配比不加更伤。FAQ 全文通常不超过 6–8 条；两类并存时决策类通常占更多。材料不足就少写，不能为了数量制造问题。机理拷问发现的正文缺口先回填正文，不计入 FAQ 预算。

## 3. 机理 FAQ

先找对象中最反直觉的机理，善用“为什么不是相反情况”定位读者误解：

1. 提出反面锚定的问题。
2. 判断答案是正文缺口还是边界澄清。
3. 正文缺口回填正文；只有补充边界和反直觉解释才留在 FAQ。

每条结构：

- 一句话纠误；
- 机理解释及适用边界；
- 对读者下一步理解的启发。

涉及闭源系统或不可直接观察的机理时，显式标记为确认、推断或类比，不把合理猜测写成事实。

## 4. 决策 FAQ

把发现翻译成 PM 要拍的 why/whether 判断，不写操作型 how：

- 做不做；
- 何时别做；
- 成本或投入量级；
- 什么条件会翻盘；
- 如何用最小验证关闭不确定性。

每条结构：明确立场（该反对就直接写“不要做”）→ 为什么及主要权衡 → 能推翻该立场的一个追问或条件。

只选非显而易见、可回溯到正文发现、且正文尚未重复回答的问题。决定性判断必须升格到顶部 verdict，不留在 FAQ 里。

## 5. HTML 表达

使用原生结构，并沿用页面已确定的视觉语言：

```html
<details class="faq">
  <summary>问题写成读者真实会问的一句话</summary>
  <div class="faq__answer">
    <p><strong>立场：</strong>先给一句话答案，再解释边界与翻转条件。</p>
  </div>
</details>
```

summary 在折叠状态下也必须可理解；不要依赖 hover、脚本或颜色表达问题类型。
