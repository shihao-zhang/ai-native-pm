# 编辑型报告 HTML

把密集材料转化为自包含 HTML：先确定内容边界与阅读契约，再按关系设计页面，最后经过结构审计和独立审校。模板只提供可选骨架，视觉表达按内容设计。

## 任务边界

先按本轮交付对象选流程。修订PRD及其同源HTML，沿项目的PRD生成链；修改可交互原型或应用，沿其实现流程。若要求基于PRD另做老板汇报、调研简报等独立静态HTML，可用本skill制作派生阅读件，标清产品定义来源与版本，不反向改写权威PRD。仅提到“HTML”“美化”“可视化”或资料较长时，不擅自选报告形态；只有交付对象确实含糊且会影响工作方式时才澄清。

## 1. 先确定来源模式

### 来源模式

- **`source-closed`｜封闭源编辑**：用户把已提供材料视为完整信息边界、只要求制作或优化 HTML，或明确禁止联网。可以重组、压缩、建立阅读路径和视觉关系，不得停留在包装美化；保留完整用户请求中的任务 framing、原始事实、判断和不确定性，不新增外部事实、数字、日期、比较对象或因果关系。材料里的链接只算已提供的引用，不等于已读取链接正文。
- **`source-expanded`｜扩展源综合**：用户明确要求研究、更新或事实核查，或种子材料本身是论文清单、阅读指南、链接索引，且任务结果依赖链接正文。先从种子材料盘点来源与拟扩展范围；取得联网授权后再读取授权范围内的来源，完成关键来源覆盖、跨来源综合和主张追溯。尚未取得授权时保留该模式判断，一次性说明范围与影响并请求授权，不静默降级成封闭源编辑。

链接只是正文脚注、用户已提供完整底本，或用户明确要求只用给定材料时，不因出现 URL 自动扩展。进入 `source-expanded` 时，完整读取 [references/source-expansion-and-learning.md](references/source-expansion-and-learning.md)；该文件按来源任务与学习目标判断是否启用深度研学要求，不依赖页面模型名称。

来源与结论状态分开表达：

- 来源类型：一手材料 / 独立复核或同行评审 / 二手转述 / 来源类型未知。
- 结论状态：确认 / 推断 / 类比 / 待验证。

状态定义：**确认**仅表示当前材料直接支持该表述，不暗示已独立验证；**推断**是由已列前提导出的编辑或决策判断；**类比**借用相似对象帮助理解，不能充当本对象证据；**待验证**表示缺少关闭问题所需的材料。来源类型未知时如实写未知或省略标签，不把“用户给定材料”冒充一手来源。

不要把“官方或一手”自动等同于“证据更强”。在 `source-expanded` 中，只对决策关键、存在冲突、具有时效性或用户明确要求核验的主张做针对性复核；二手材料确实影响核心结论时，才制作“属实项 / 需校正项 / 常见缺失项”核查卡。

### 视觉选择

按内容关系与阅读目标设计，遵循设计准则，不预设固定配色、圆角、阴影或单栏布局。优化已有 HTML 时优先延续其有效视觉语言。脚本能力与视觉选择独立，工程底线与零脚本需求按设计准则第 7 节处理。

“适合飞书分发”只表示文件自包含、易上传或静态托管；具体发布到飞书文档、妙搭或其他载体前，单独确认目标接口。

## 2. 确定主阅读契约

读取 [references/design-rubric.md](references/design-rubric.md)，先判断以下常用配方是否合适；均不合适时，按其中的自定义出口与人类对齐。始终让一个主要阅读目标主导：

- **决策简报**：结论 → 判断轴 → 证据与权衡 → 决策门 → 开放问题。
- **对比报告**：范围与坐标轴 → 对象画像 → 归一化矩阵 → 权衡 → 建议 → 验证缺口。
- **长篇手册**：索引或角色入口 → 章节地图 → 章节 → 步骤与示例 → 自检 → 术语和来源。

首屏围绕主要阅读目标建立清晰层级，判断数量与入口形式由内容和实际视口决定。需要多章往返查阅，或读者希望先快速掌握全貌、再按需深入时，读取 [references/handbook-navigation.md](references/handbook-navigation.md)，分别选择导航与阅读深度方案。明确要求速览模式时，应呈现重组后的整篇精华视图，不能仅用全文第一章代替；不要把逐章专注误作整篇速览，也不自动叠加多个模式。

内容深度与表达方式分别决定：研究或 PM 报告也可用直观关系图引导阅读。重组前先明确不可丢失的核心主张、架构关系与关键条件，再按读者问题安排主线和深读；补充材料不自动新增章节。具体取舍与渐进阅读见设计准则。

深度研学的启用条件与要求以来源参考第 5 节为准；自定义契约不会豁免适用的来源综合与学习要求。

## 3. 把内容关系转成页面关系

- 按理解任务选择表达：短段落、表格、流程、时间线、卡片或组合形式均可。容器和布局应帮助读者看见真实关系，不把字段重复当作必须用表格的条件。
- 视觉几何必须忠实于语义：闭环要显示反馈边，阶段要保持顺序，比例图不得暗示材料未支持的规模关系。正文要求读者打分、勾选、标记或选择时，提供原生控件或可打印标记位，不能只写操作说明。
- 避免机械地给每段套框。图可用于关系解释、视觉证据、界面示例或概念理解；需交叉引用时编号，读法、来源或边界需要说明时加图注，避免完整复述。
- 输入包含图片目录、`image_inventory` 或批量源图时，先把每张图标为 `transcribe`、`preserve`、`exclude` 或 `dual`，再实现页面。“务必嵌图”默认表示图片独有信息不得遗漏，不等于逐图原样展示；同一信息不得同时以完整 HTML 表格和原始表格截图重复出现，除非二者各有不可替代信息且图注明确说明差异。具体分流见 [references/design-rubric.md](references/design-rubric.md)。
- 只在重要、易争议或影响决策的主张附近标来源类型与结论状态，不给每一句话挂徽标。
- 未知的 DOC 编号、版本、日期或受众字段直接省略或标待确认，不制造看似正式的占位事实。

## 4. 实现页面

- 按结构需要选择骨架：连续报告可参考 [assets/editorial-base-template.html](assets/editorial-base-template.html)。需要速览 / 全文时，先读取 [assets/handbook-template.html](assets/handbook-template.html)，优先复用其阅读外壳与切换实现；仅需章节导航时独立复用目录与当前章逻辑，布局按导航参考选择。颜色、图形和速览内部构图按材料设计，不机械填槽。均不合适可自建语义骨架。`decision-only` 仅在需要结论与行动门时保留；模板不决定阅读契约。
- 语义、无障碍和工程底线统一见设计准则第 6–7 节，不由配色或模板决定。
- 手册不得用 JavaScript 把“可读文档”改成必需交互的 App：默认全文可读，速览或逐章专注只按阅读需要提供；深读入口使用真实锚点，切换与 hash、浏览器历史一致，无脚本和打印时保留完整内容。实现契约见导航参考。
- 长 HTML 先建立包含闭合标签的完整骨架，再用 patch 分段填充章节；不要 append 未闭合文档后运行完整审计。结构成形后审计一次，每轮实质修改后再审计。

## 5. 初稿后的独立审校闭环

初版 HTML 完成后读取 [references/review-and-faq.md](references/review-and-faq.md)：

1. 先运行确定性结构审计。
2. 对非平凡报告，如果当前环境提供 subagent，先告诉用户本 skill 将启动一次只读审校，再把“完整用户请求 + 原始材料 + 初版 HTML + skill 路径”交给一个无先验结论的 subagent；禁止其改文件。满足任一条件即可视为非平凡：超过 5 个章节、正文约 1500 个汉字以上、多来源或多对象对比、包含会影响资源投入的决策建议。
3. subagent 检查阅读契约、来源模式与覆盖、证据边界、源图去重、视觉转译和工程质量，并执行 FAQ 梗阻诊断；不适用的检查跳过，只返回 findings 和建议 delta。
4. 主 session 对照完整用户请求逐条判断 findings，拒绝因 reviewer 缺上下文产生的误报；裁决补充、合并、删减或下沉，保留核心洞察与必要条件，按需增加 FAQ，不机械接受所有建议。
5. 修改后做一次只针对 delta 的内容忠实性复核，再运行结构审计；不要递归启动第二轮开放式 review。
6. 如果没有 subagent，或 spawn 超时、路径不可读、返回结果缺少证据，主 session 按同一清单自审并如实说明。

FAQ 不是交付必选项：先判断读者卡在理解、行动、两者还是都不卡。需要时，机理 FAQ 放在相关机理之后或决策之前，决策 FAQ 放在收尾；两类合计通常不超过 6–8 条，材料不足就少写，不凑数。正文缺口必须回填正文，不计入 FAQ 预算。HTML 使用原生 `<details><summary>`，沿用既有视觉语言。

## 6. 验证与交付

运行：

```bash
node scripts/audit_html.mjs <输出.html> --fail-on-warning
```

用户或交付环境要求零脚本时加 `--no-scripts`。审计不再提供风格或 profile 选项。

该脚本仅作确定性结构检查，不能证明事实、来源覆盖、图像语义或审美。质量与验收规则以设计准则第 5–9 节为准；脚本实现可确定判断的检查，模板展示用法，不另行定义标准。所有 warning 都要修复或在交付中明确解释。

HTML 默认面向电脑宽屏，不主动做手机竖屏适配或验收；仅在用户明确要求或项目已有移动端要求时，增加对应适配与移动视口验收。保留已有移动端支持，不因默认范围调整而删除。浏览器可用时至少检查一个桌面宽屏视口和打印预览，按需验证交互，并记录实际测试的视口尺寸。报告含时效性判断或决策建议时，在 footer 写明“什么信号出现就应回炉更新”。

本地预览与浏览器验收先读取包内的 [references/html-preview.md](references/html-preview.md)，按当前工具能力选择路径，处理服务归属、版本与取证。宿主明确提供的本地操作指南仅补充环境特有设置；技能本身不依赖包外文件。

最终交付一个独立 `.html`；若目标是某个发布平台，另行确认部署方式。

对已有成品做信息结构或视觉改版时，保留可直接打开的改前、改后独立文件，并在交付中给出两个入口；用户明确要求覆盖时遵从其要求。技术审计、内容审校和渲染结果分别说明，不能据此宣称信噪比或体验已改善；改版收益作为待用户比较的判断。

## 7. Review 现有 HTML

只做 review 时不要改文件，也不要因发现外链而自动进入 `source-expanded` 或重写内容。从五个角度给结论：阅读路径、编辑转译、可信度、工程质量、与明确约定的视觉要求是否一致。在多份候选中优先选择内容模型最强、源码结构最干净的文件，不自动选择视觉最复杂的一份。
