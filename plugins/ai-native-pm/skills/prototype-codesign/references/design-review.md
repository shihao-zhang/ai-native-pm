# 设计走查与修复闭环

供设计对齐时按需使用；按已定设计施工或独立验收者可直接读取本件，不因此承担共创任务。项目阶段沿用[四状态](workflow.md)，问题记录是逐项进展，不是第五个项目状态。

## 从差异找到当前承接人

固定受检对象及状态，对照已确认设计或有效DS，再选择下一动作。下表是处理路由，未核清时不强行判定根因：

| 当前需要解决什么 | 谁承接、如何继续 |
|---|---|
| 原型没有还原已定要求 | 当前原型维护人修复；正式工程阶段按实际写区归属处理，不默认派给前端 |
| 怀疑DS版本、能力或规范冲突 | 先核消费版本/接入，接入偏差由消费方修；确认正式缺失或冲突才交DS维护方 |
| 设计位置、层次、状态或范围未明确 | 设计负责人明确后再执行 |
| 产品语义、命名或操作取舍未定 | 产品负责人裁定；影响业务规则时回方案对齐 |

每项明确一个当前承接方，后续接收方可以另列。优先级独立于路由；待核是证据状态，不是第五种根因。设计笔误、已接受差异单列，不为还原样例新增业务能力。

## 复用现有问题记录

需要追踪时，现有表能串起“问题/位置—受检版本与复现状态—依据—当前承接和动作—复验结果”即可；不强制新建台账或填写不相关字段。设计已明确的项继续处理，依赖只阻塞受影响部分。同源问题可合并修，保留各问题与修复的对应关系。

已确认的设计约束执行自由度；只有未确定部分由执行方结合DS选择。不同会话并行写时划清写区，必要时用隔离分支/候选，合并时保留双方有效改动，不整包覆盖。

关闭项前，在受检新版本重现原操作及状态，确认差异消失且相关业务边界保留。代码/模型绿灯、已回复和已接单均不能直接当关闭；证据分层及接收副本检查统一见[证据与复验](evidence-review.md)。复核按具体发现分工并回源判断，修后复验该发现，不以多人投票或反复泛审代替核验。设计与PM确认沿已有约定，不增通用审批门。

例：默认页输入框正确，进入调试后恢复却退回单行高度，说明复验需要覆盖该恢复状态。颜色使用了某个DS变量，也不等于其状态语义映射已被DS确认。这些是实例提醒，不指定固定画幅、测试数、配色或评审人数。
