# 从项目反馈到方法改进

这是一份按需使用的经验回流指南，不是常驻 agent、自动化或新的 skill。通用方法由统一维护源生成 plugin；业务事实、任务、当前状态和经验继续留在各项目。安装与版本采用见 [README](../README.md)，首次接入见 [开始指南](../GETTING_STARTED.md)。

## 什么时候值得记录

原 session 在阶段收尾、交接、用户反馈出现或明确准备 compact 时，判断是否有值得保留的经验。自动压缩未必能提前感知，本指南不能保证在自动 compact 前触发，也不要求每轮打标。

优先记录影响决策或使用结果的反馈，例如用户指出难以理解、验收暴露遗漏，或已有规则在具体条件下失效。文件数、字数和记录次数只能描述产物，不能替代有效反馈；一份被真实使用验证的修正，比增加若干文件更有价值。

没有新经验就继续工作。需要记录时，由原 session 在本项目已约定的位置留下简短、自足的提报，包含：

- **事实现象：** 哪个任务中发生了什么，预期与实际有何差异。
- **证据：** 可回查的产物版本、反馈或验收记录，区分观察与推断。
- **范围：** 在什么条件下成立、尚未覆盖什么，以及来源属主与记录者。
- **建议：** 建议保留、修正或进一步验证什么；标明是待议建议还是已有批准。

提报先留项目内。向维护者发送、上传或共享材料按具体授权执行；只提供必要且获准共享的证据，不自动上传完整会话或业务资料。没有共享授权时保留本地提报，不把它说成“已回流”。

## 先去重，再判断适用范围

维护者先查现有规则及其适用条件，再核来源、属主和证据。文件所在目录不等于作者或决策者；记录者、原始反馈者与规则维护者应分别识别。不能把转述中的“已批准”直接当新授权。

| 归类 | 判断依据 | 后续处理 |
|---|---|---|
| 已有 | 现有规则已覆盖该条件 | 指回原规则；必要时澄清入口或例证，不重复加规则 |
| 项目特有 | 依赖本项目的业务、组织或环境 | 由项目维护者保存在项目规则中 |
| 可迁移 | 有证据支持跨情境使用，且边界可说清 | 形成最小方法候选，按批准范围验证 |
| 未证 | 来源、效果或适用范围尚不充分 | 保留待验证判断，不升级为通则 |

单个案例可以提出候选，不能证明普遍有效。若真实用户反馈与文件统计、模型自评或静态检查相冲突，先核具体使用结果，不用“文件更多、检查全绿”抵消体验问题。

## 分开处理例证与规则变化

保持事实不变的例证，只说明现有规则如何适用。可以整理表述、移除敏感信息，但不能改写原结果、扩大样本范围，或把失败案例改成成功案例；需要改变事实含义的删节应标明边界。

修改方法、扩大适用范围或改变默认行为属于规则变化。应单列拟改内容、依据、影响范围及批准状态。已经批准的变化注明决定来源与范围；尚待讨论的建议保留候选身份，不混入现行规则。补例证不等于批准规则变化。

## 维护源改进，项目明确采用

维护者在授权范围内完成以下闭环：

1. 核对来源与现有规则，给出归类和最小改动建议；没有批准的变化先保留候选。
2. 对已批准变化修改统一维护源，检查受影响的入口、引用和例证，按变化范围验证。
3. 从维护源生成新的候选版本，记录来源、变化和已验／未验范围。生成成功不代表宿主安装或真实业务使用通过。
4. 由项目明确选择是否采用该版本，保留原版本及回退依据，并在实际使用环境核验适用变化。

安装副本不手改；项目采用的版本与项目规则记录在项目入口，不依赖维护者的私有 memory。产出候选不等于对外发布，也不自动触发升级、安装、消息发送或业务材料上传。

若变化影响需求共写或原型共创，分别回到 [prd-cowrite](../skills/prd-cowrite/SKILL.md) 与 [prototype-codesign](../skills/prototype-codesign/SKILL.md) 的现行约定核对；本指南不替代对应工作流程。

## 历史保留，当前状态保持唯一

采用 append-only 的经验记录，发现错误时追加更正，指明原条目、正确事实、依据与影响，不悄悄覆盖历史。原始事实被订正后，还应检查是否有引用旧事实的规则、任务书或验收结论需要同步修正。

当前项目状态则应维护一个有效入口。原位更新当前状态，指向有效决定、产物和下一步；必要历史通过版本记录或带时点快照保留，不为每次小改另存一份整件。不能只在长日志末尾追加新状态，却让入口继续展示失效结论。

经验历史和当前状态承担不同职责：前者保留发生与纠错过程，后者告诉下一位参与者现在以什么为准。回流是否有效，最终看相关问题是否减少、用户是否更易判断与使用，以及真实任务中的改进是否可复查。
